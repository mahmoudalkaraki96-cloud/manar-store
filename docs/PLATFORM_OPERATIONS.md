# إدارة المتاجر — platform-0.1.0

هذه المرحلة أدوات تشغيل وسجل موارد، وليست لوحة اشتراكات أو نظام إنشاء متاجر آليًا. نسخة واجهة المتجر الحالية تبقى كما هي في VERSION. لا يغيّر هذا الإصدار بيانات أو تصميم منار أو ركن، ولا يغيّر إعدادات Cloudflare Access أو صلاحيات حساباتهما.

## الموارد والتحديثات

`platform/stores.json` هو سجل المتاجر. ملفات Wrangler الحالية تبقى مصدر إعدادات التشغيل الخاص بكل عميل؛ لا ننسخ إعدادات منار إلى ركن. أداة النشر تتحقق من تطابق قاعدة البيانات والصور والـWorker ومن عدم اشتراك متجرين في الموارد. بيانات المنتجات والشعار والألوان في قاعدة بيانات كل متجر، والأسرار في Cloudflare وGitHub فقط.

منار مفعّل لعمليات النشر المدروسة، لكن يتطلب كل نشر تأكيد فحص نفس commit على معاينة خاصة. ركن مسجل ومعطّل للنشر المركزي حتى مراجعة الدومينات وهوية المدير وبيانات Push والـbindings والمعاينة. إعداداته الحالية لا تعرّف ADMIN_OWNER_EMAIL أو ADMIN_CF_AUD؛ لا يجوز اختراعها أو نسخ مالك منار إليه. لا تُعتبر كلمة «مسجل» إثباتًا لرقم نسخته الحية.

## عرض خطة بلا اتصال أو تغيير

```sh
node scripts/platform-release.mjs --store manar --revision FULL_40_CHARACTER_COMMIT_SHA
node scripts/platform-release.mjs --store all --revision FULL_40_CHARACTER_COMMIT_SHA
```

الاختيار إلزامي. يمكن أيضًا تحديد `manar,rokon`، ولا يُقبل اسم مجهول أو فرع متغير مثل main. الأمر افتراضيًا يعرض خطة فقط، ولا ينشئ موارد أو يطلب API أو يكتب في قاعدة بيانات.

Workflow «Platform store releases» يوفر نفس المعاينة من GitHub Actions؛ execute افتراضيًا false. مسار النشر القديم لمنار ما زال كما هو؛ لا ننقل النشر التلقائي إلى كل العملاء ضمن تحديث أدوات التشغيل.

## تنفيذ إصدار معتمد

1. بناء commit محدد وفحصه على معاينة محمية فعليًا. لا تكفي noindex أو سرية الرابط لحماية المعاينة. لا تفعّل المعاينة بطلبات كتابة أو رسائل حقيقية على بيانات الإنتاج. إنشاء هذه المعاينة غير منفّذ ضمن هذه المرحلة.
2. التأكد من إعداد هوية المدير وصلاحياته وPush والصور والروابط للمتجر المقصود؛ ثم تفعيل release.enabled له في مراجعة منفصلة.
3. من workflow اختر المتجر وcommit نفسه، وأدخل SHA في verified_revision بعد الفحص، ثم execute=true. هذا إقرار المشغّل بإتمام المعاينة وليس تحققًا آليًا منها. لا تفعّل all قبل جاهزية كل المتاجر.
4. الأسرار المطلوبة: CLOUDFLARE_API_TOKEN بصلاحيات الموارد المحددة، CLOUDFLARE_ACCOUNT_ID الصريح، PLATFORM_BACKUP_PASSPHRASE قوية ومحفوظة خارج سجل التشغيل. لا يختار النظام أول حساب Cloudflare تلقائيًا.
5. يُشغَّل الاختبار والبناء، ويؤخذ تصدير D1 وقائمة إصدارات Workers لكل الأهداف قبل أول migration. لا يعاد تشغيل db/rokon-init.sql عند كل تحديث، لأنه إجراء تهيئة منفصل.
6. يطبّق migrations ثم ينشر المتجر والإدارة بتحديد --config دائمًا. تتوقف العملية عند أول فشل، ويُحفظ تقدم كل خطوة. لا يوجد transaction موزع بين Workers أو المتاجر؛ قد ينجح جزء قبل الفشل.
7. نتيجة النجاح هي deployed-awaiting-live-verification. تُفحص الواجهة والدخول والبحث والسلة والصور والإشعارات قبل تسجيل النسخة كنسخة حية متحقق منها. لا يعني نجاح أمر deploy نجاح جميع الوظائف.

للتنفيذ المحلي بعد `npm ci` والبناء والاختبارات، على checkout نظيف لنفس commit:

```sh
node scripts/platform-release.mjs --store manar --revision SHA --verified-revision SHA --execute
```

تنفيذ محلي يحتاج Git وNode وWrangler المثبت من lockfile، وإعداد حساب Cloudflare الصريح. لا يُفترض أن كل متجر يدعم كل المزايا قبل فحص إعداداته.

## السجل والنسخ الاحتياطية والرجوع

`release-artifacts/<timestamp>-<sha>/release.json` يسجل الإصدار المطلوب والـcommit والخطوات الناجحة والفشل. معه تصدير D1 وقوائم إصدارات Workers السابقة. محليًا هذه ملفات خاصة قد تحتوي بيانات زبائن؛ لا ترفعها إلى GitHub ولا تشاركها. في Actions تُجمع وتُشفَّر AES256 بكلمة السر من Secrets، ويرفع الملف المشفر فقط لمدة30 يومًا. إذا فشل الرفع أو التشفير يُراجع التشغيل ويُعاد تأمين النسخة؛ لا يُفترض أن وجود خطوة التصدير وحده يعني حفظًا خارجيًا ناجحًا.

الرجوع إلى Worker سابق يتطلب نسخة متوافقة مع schema الحالية. لا تعاد قاعدة البيانات تلقائيًا فوق الطلبات الجديدة. عند خطأ migration تُراجع التغييرات والنسخة الاحتياطية ويحدد إصلاح أمامي أو استعادة مدروسة. راجع سجل التشغيل لكل متجر؛ لا تستنتج نجاح بقية المتاجر من نجاح منار.

## تجهيز عميل جديد

1. جمع اسم المتجر ودومينه وبريد مالكه والباقة المطلوبة؛ لا كلمات مرور في الملفات.
2. إنشاء D1 وR2 مستقلين وWorker للمتجر وآخر للإدارة، مع معرف STORE_KEY خاص بالعميل. إعداد مالك الإدارة ووسيلة Cloudflare الاختيارية والأسرار الخاصة به، وعدم نسخ هوية مالك منار.
3. تطبيق migrations بعد مراجعة ملاءمتها لعميل جديد؛ التهيئة من قالب عام خاص بالعميل دون استيراد منتجات أو زبائن منار. بعض migrations التاريخية خاصة بمتجر منار، لذا لا تعد هذه الخطوة تلقائية أو جاهزة قبل تدقيق خط أساس التهيئة.
4. ضبط الشعار والألوان والشحن وسياسات المتجر وروابطه، وربط الدومين وتحقق TLS وDNS.
5. تسجيله في السجل مع release.enabled=false. فحص معاينته والدخول والصور وطلب تجريبي في بيئة معزولة، ثم اعتماد تفعيله للنشر.

التالي: تدقيق خط أساس قاعدة متجر فارغة، تجهيز معاينة خاصة حقيقية، ثم أتمتة إنشاء الموارد. لوحة إدارة المنصة والاشتراكات ودعم الدخول المسجل من لوحة المالك مراحل لاحقة؛ غير منفذة بهذا الإصدار.


## تحديث platform-0.2.0 — تدقيق حي ومعاينة منفصلة

الفحص الحي في2026-10-29 أكد أن rokon-store الحالي مربوط بـmanar-store-db وmanar-store-media، بخلاف ملفات Wrangler المقصودة. الوصف السابق لاستقلال الموارد كان تحققًا من ملفات المستودع فقط، وليس إثباتًا للربط الحي. runtimeAudit.status=mismatch يمنع النشر حتى لو فُعِّل release.enabled خطأً؛ لا يجري فصل أو تبديل الموارد تلقائيًا.

المعاينة الجديدة تستخدم مدخل worker/preview.ts وبناء STORE_PREVIEW_BUILD=1، دون D1/R2/AI أو cron أو أسرار متاجر. تقرأ فقط مسارات الكتالوج/الواجهة/السياسات/الشحن والصور العامة من manarstore.ps، دون تمرير Cookie أو Authorization أو بيانات زوار. جميع الكتابات وحسابات وإدارة وPush وServiceWorker ممنوعة، وCSP يمنع تتبعًا خارجيًا. نسخة الواجهة نفسها تُبنى من الفرع المختار، فلا تحتاج نسخ منتجات أو طلبات.

scripts/build-preview.sh يبني المدخل المستقل ويجهز .preview-release.jsonc برقم commit الحقيقي. scripts/prepare-preview.mjs يرفض artifact لا يحوي بوابة المعاينة أو config يحتوي binding لقاعدة/صور. Wrangler assets.run_worker_first=true يحمي الملفات الثابتة أيضًا. JWT موقّع RS256 وissuer/audience/exp/iat/nbf وقائمة البريد كلها مطلوبة، ولا تُقبل ترويسة بريد غير موقعة. غياب إعداد حماية Access أو غياب JWT يمنع كل المحتوى افتراضيًا.

Workflow Private storefront preview يفحص ويبني فيPR؛ النشر يدوي deploy=true ويستهدف manar-store-preview وحده. بعد نشره يضاف hostname الجديد إلى تطبيق Access الخاص بمنار بنفس سياسة المالك، دون تغيير مسارات الإدارة أو معاينات ركن. /__preview/status يعرض SHA المحمي للفحص؛ إقرار verified_revision في أدوات النشر يجب أن يطابقه. هذه المعاينة لفحص واجهة المتجر والبحث والسلة المحلية؛ لا تختبر حفظ الطلب أو صلاحيات الإدارة أو migrations لأنها لا ترتبط بقاعدة البيانات. ركن يحتاج خطة فصل موارد ومراجعة مستقلة قبل التعميم.
